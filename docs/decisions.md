# 설계 결정 기록 (ADR)

기획서(v0.1)의 ADR 을 이어서, 구현 중 내린 결정과 그 근거를 적는다. "측정/확인"은 실제로 해 본 것, 나머지는 판단이다.

## ADR-008 Spark 대신 Trino MERGE
- 맥락: Docker VM 7.75GB 중 다른 프로젝트가 약 3.8GB. 기획 메모리 예산(Spark 3·Trino 2·ClickHouse 2GB)은 들어가지 않음.
- 결정: silver 반영을 Trino `MERGE INTO`(Iceberg)로. 대량 append(bronze·stage)는 PyIceberg.
- 근거(확인): Trino MERGE 가 조건부 `WHEN MATCHED AND … THEN UPDATE`, `WHEN NOT MATCHED AND … THEN INSERT` 를 지원해 SCD2 를 한 문장으로 쓸 수 있고, 한 문장 = 한 스냅샷.
- 대가: `NOT MATCHED BY SOURCE` 가 없어 원천을 UPSERT·NEWVER·MISSING 세 갈래로 합성해야 함.

## ADR-009 SCD2 는 한 문장 (U-4)
- 두 단계(닫기 → 삽입)면 사이에 실패할 때 현재행이 없는 거래가 생길 수 있고, 재실행 조건을 따로 설계해야 한다.
- 한 문장이면 커밋 단위가 하나이고, 같은 stage 로 재실행하면 모든 행이 '속성 같음'으로 매칭돼 불변 (통합 테스트로 확인).

## ADR-010 카탈로그 = Lakekeeper + vended credentials (U-1)
- Trino·PyIceberg 는 스토리지 키를 설정하지 않는다. Lakekeeper 가 catalog 계정으로 MinIO STS AssumeRole 을 해 테이블 경로 범위 단기 자격증명을 준다.
- 확인: 웨어하우스 생성 시 Lakekeeper 가 저장소 검증에 성공, Trino MERGE·PyIceberg append 모두 이 방식으로 동작.
- 한계: 로컬에서는 카탈로그 인증 없음(allowall) — 도커 네트워크 안 + 호스트 127.0.0.1 만. 운영이면 OIDC.

## ADR-011 Dagster 파티션은 계약월, 시군구 상태는 Postgres 상태 머신
- 256 × 수백 개월의 Dagster 파티션은 실행·이벤트 로그 오버헤드가 수집(호출 1회 ≈ 0.1~0.3초)보다 크다.
- 월 실행 안에서 시군구를 동시 4개·초당 10회로 수집하고, 시군구 단위 상태(PENDING→FETCHING→LOADED→MERGED / RETRY / QUARANTINED)는 `ops.ingest_partition` 에 둔다.
- 시군구 단위 재실행: 관리 API 재시도 → 센서가 그 시군구만 run config 로 요청.

## ADR-012 예산은 Redis Lua + 우선순위 상한 + 센서 계획
- 상한 = 일 한도 × 80%. 증분 몫(시군구×3), 재확인 몫(시군구×12, 대기 중일 때만)을 하위 우선순위가 쓰지 못하게 우선순위별 상한을 둔다.
- 실행 안의 차감은 Lua 로 원자적 (100 스레드 동시 차감 → 정확히 상한, 통합 테스트).
- 센서는 이미 큐에 있는 실행의 예상 호출 수까지 빼고 계획한다 (없던 시절 한 틱에 52개 실행이 쌓이는 문제를 실제로 겪음).

## ADR-013 공개 API 와 관리 API 를 프로세스로 분리
- 기획의 "관리 API 는 127.0.0.1 에서만"을 앱 안에서 검사하면, Docker Desktop 포워딩에서는 모든 요청이 같은 게이트웨이 IP 로 보여 의미가 없다.
- 관리 라우트를 별도 앱(:8611)에만 등록하고, 웹 프록시는 공개 앱만 전달. 공개 앱에는 관리 라우트가 존재하지 않음을 테스트.

## ADR-014 스코프 누락은 기동 실패
- 모든 라우트가 `require_scope(...)` 를 의존성으로 가져야 하고, 기동 시 전 라우트를 검사한다.
- FastAPI 0.141 은 `include_router` 결과를 `_IncludedRouter` 로 감싸 `app.routes` 에서 안쪽 라우트가 보이지 않는다 — 처음 구현은 이 때문에 검사가 사실상 비어 있었고, 테스트로 발견해 안쪽까지 순회하도록 고쳤다.

## ADR-015 발행 = 스테이징 + 대조 + 파티션 교체
- ClickHouse `REPLACE PARTITION … FROM staging` 은 원자적. 교체 전에 Trino 결과와 건수·합계를 비교해 다르면 중단.
- 소형 테이블(시군구·단지·지수)은 `_next` 테이블 적재 후 `EXCHANGE TABLES`.
- 발행이 끝나야 데이터셋 버전이 올라가고, API 결과 캐시 키가 버전을 포함하므로 캐시 무효화가 자동.

## ADR-016 정확 분위수
- `approx_percentile` 은 근사라 "Trino 결과 = ClickHouse 결과" 수용 기준을 설명하기 어렵다. 선형 보간 정확 분위수를 window 함수로 구현(dbt 매크로), numpy 와 차이 0.0 확인.

## ADR-017 지수는 수집이 완결된 달만
- 백필 도중 2024-07 에는 시험 수집한 2개 구만 있었고, 전국 지수 기준월이 그 두 구의 추세를 따라가 2024-08 이 +23% 로 튀는 것을 실제로 봤다.
- 규칙: 시군구 90% 이상 MERGED 인 계약월만 지수 입력. 제외된 달은 실행 메타데이터에 남긴다.

## ADR-018 추측 값 금지
- 시군구 코드·이름은 행안부 법정동코드 API, 지수 기준값은 R-ONE 통계표에서 가져온다.
- 약칭 → 시도 코드처럼 표가 필요해 보이는 곳도 공식 명칭에 대한 결정적 규칙(유일할 때만)으로 매핑하고, 모호하면 매핑하지 않는다.
- 상위 시(일반구를 둔 시) 판별은 locathigh_cd 가 도를 가리켜 쓸 수 없음을 확인하고, 공식 명칭 포함 관계를 쓴다.

## ADR-019 발행 대기 상태를 따로 추적 (실패 복구)
- 겪은 문제: 실행이 silver 반영 뒤·ClickHouse 발행 전에 죽으면(컨테이너 재시작), 그 달의 원천 파티션은 이미 MERGED 이고
  다음 수집은 원본 해시가 같아 bronze·silver 가 산출물을 내지 않는다 → gold·발행이 다시는 실행되지 않아 **서빙에서 영구 누락**
  (실제로 2026-06·07 이 silver 에는 있고 ClickHouse 에는 없었다).
- 결정: `ops.month_state.needs_publish` — silver 반영 성공 시 true, 발행 성공 시 false.
  bronze 에 `fetch=False`(원천 호출 없음) 모드를 두고, 센서가 발행 대기 달에 호출 0회 실행을 요청한다.
  이때 silver 는 반영 없이도 현재 레이크 상태(현재행 vs 마지막 stage)로 blocking 검사를 **다시 계산**해 통과해야 하위로 넘긴다.
- 발행은 스테이징 대조 + 파티션 교체라 같은 달을 여러 번 발행해도 결과가 같다 (V003 마이그레이션이 기존 반영 달을 전부 한 번 재발행하도록 표시).

## ADR-020 원천 한도 초과는 '격리'가 아니라 '오늘은 중단'
- 겪은 문제: 포털이 일일 한도 초과를 **HTTP 429** 로 돌려주는데, 클라이언트가 4xx 를 영구 오류로 보고 시군구 파티션을 즉시 격리했다.
  한 달 전체(256개)가 격리돼 blocking 검사(격리율 < 20%)가 하위 반영을 막았고, 1,290개 파티션이 잘못 격리됐다.
  (검사 자체는 의도대로 동작해 잘못된 데이터가 퍼지지 않았다 — 분류가 틀렸다.)
- 원인: 내부 카운터는 7,170회였는데 포털은 한도 초과. 한도는 인증키 단위라 같은 키를 쓰는 다른 프로그램의 호출도 합산된다.
- 결정: HTTP 429 또는 포털 오류 봉투의 사유 코드 22 → `QuotaExceeded` (실행 중단, attempts 되돌림).
  그날 예산을 상한까지 채워 `exhausted_by_source` 사유와 함께 기록 → 센서는 KST 자정까지 수집 실행을 만들지 않는다.
  잘못 격리된 파티션은 사유를 남기고 RETRY 로 되돌렸다. 키 오류(30 등)는 여전히 즉시 실패.

## ADR-021 Trino 메모리: 힙이 아니라 프로세스 전체(RSS)로 한도를 맞춘다
- 겪은 문제: 단지 차원 전체 재생성(dbt `complex_summary`) 중 Trino 가 컨테이너 한도 2GB 에서 OOM-kill.
  힙 1.4GB + 코드 캐시·다이렉트 버퍼·메타스페이스·스레드 스택이 합쳐 한도를 넘었다.
- 결정: 힙 1.2GB, `MaxDirectMemorySize=256M`, `MaxMetaspaceSize=256M`, 질의 메모리 600MB. 같은 작업에서 최대 1.8GiB 로 측정.
- 함께: 상주 서비스 전부 `restart: unless-stopped` (그 전에는 죽으면 그대로 멈춰 있었다).
  수동 실행(`make month·index·maintenance`)은 `job launch` 로 큐를 거친다 — 센서 실행과 한 컨테이너 메모리를 동시에 쓰다
  지수 산출 프로세스가 SIGKILL 된 적이 있다. 지수 입력은 문자열을 사전 인코딩 정수로만 다뤄 최대 RSS 980MB.

## ADR-022 지도 경계: V-World 시군구 경계, 시군구별 단순화
- 출처: 국토정보플랫폼 V-World `LT_C_ADSIGG_INFO`. 반영 조건은 코드·공식 명칭이 행안부 시군구 목록과 일치하는 것만 (256/256 일치, 불일치는 추측하지 않고 보고). 원본은 raw 버킷에 내용 주소로 보관.
- 원본 52.6MB · 점 1,346,568개 → 웹에 그대로 보낼 수 없다. 비교한 방법:
  - topojson(공유 경계 단순화): 수집 프로세스 최대 메모리 3.2GB → Dagster 자식 프로세스가 죽음(`ChildProcessCrashException`). 탈락.
  - GEOS `coverage_simplify`: 원본 이웃 경계가 꼭짓점을 공유하지 않아(각 시군구가 따로 디지타이즈됨) 점이 약 20만 개까지밖에 안 줄었고, 퇴화 고리(점 2개) 오류도 났다. 탈락.
  - **시군구별 Douglas-Peucker 0.001°(위상 보존) + 0.5㎢ 미만 조각 제거 + 0.0001° 격자 정렬**: 최대 메모리 약 0.5GB, 점 58,923개(4.4%).
- 품질을 숫자로 남긴다: 면적 상대 오차 중앙값 0.07%·최대 1.91%, 단순화 후 이웃끼리 겹침 0.037%·원본 대비 틈 0.011% (`ops.region_boundary.simplify`, 검사 `boundary_matches_official_regions`).
- 응답 1.1MB → gzip 292KB, `Cache-Control: max-age=86400` + ETag. 경계는 매월 시군구 목록 갱신 작업과 함께 다시 받는다.

## ADR-023 웹은 BFF — 브라우저에 키를 두지 않는다
- 웹 화면이 anonymous 한도(IP 당 분당 20)를 쓰면 지도·표·시세 띠를 한 번 여는 것만으로 한도에 닿는다. 그렇다고 키를 번들에 넣으면 누구나 꺼내 쓴다.
- 결정: nginx 가 서버 쪽 `WEB_API_KEY` 를 붙인다(`map` 으로 사용자가 보낸 `X-API-Key` 가 있으면 그것을 우선). 키는 `db-migrate` 단계에서 HMAC 만 등록, 바뀌면 이전 키 자동 폐기(감사 로그).
- 한도는 `web` 플랜(분당 300, 일 20만 행, 60개월)이고 **주체를 키가 아니라 브라우저 IP(HMAC)** 로 센다 — 한 사용자가 키 전체 한도를 다 쓰지 못하게.
- 확인: 웹 경유 `x-ratelimit-limit: 300`, 직접 호출 20, 웹 경유라도 잘못된 키를 보내면 401, IP 가 다르면 남은 횟수가 따로 줄어듦(통합 테스트).

## ADR-024 행 한도는 레코드 단위 응답에만
- 일일 '데이터 행' 한도의 목적은 원자료 대량 추출 방지다. 월 통계·지도·순위·지수처럼 원자료를 내보내지 않는 집계에 행을 매기면, 지도 한 장(시군구 256개)이 한도를 먹어 정작 막아야 할 것과 무관하게 화면이 막힌다.
- 결정: 거래 목록·거래 이력·가격 분포의 산점도 점(최대 3,000)·단지 거래 이력만 행으로 센다. 집계는 요청 수 한도만.

## ADR-025 대표값은 확정된 달, 잠정 달은 따로 표시
- 계약월 말일 + 60일 전까지는 신고가 계속 들어온다(FR-403). 가장 최근 달을 대표값으로 쓰면 거래량이 급감한 것처럼 보이고, 지수도 표본이 적어 흔들린다(실제로 2026-09 전국 지수 표본은 2026-06 의 46%).
- 결정: 시세 띠·KPI·지수 머리글·지역 비교 표는 잠정이 아닌 최근 달, 잠정 달은 차트에 음영 + '잠정' 표시, 지수 머리글에는 보조로만(값·전월비). 시장 개요의 기본 기준월도 확정 달.

## ADR-026 운영 상태 응답의 ETag 는 본문 해시
- 데이터 응답은 (데이터셋 버전, KST 날짜, 요청) 이 같으면 본문도 같으므로 이것으로 캐시 키·ETag 를 만든다.
- 운영·품질 상태는 발행과 무관하게 바뀌는데 처음에는 같은 방식을 써서, 내용이 바뀌어도 304 를 돌려주는 버그가 있었다. 결정: `cache=False` 응답은 본문을 먼저 만들고 본문 해시로 ETag (통합 테스트: 같은 요청이라도 내용이 바뀌면 200 + 새 ETag).

## ADR-027 수집 상태·오류 로그는 Dagster GraphQL 읽기 전용 + 비밀 가림
- 운영자가 원인을 복사해 공유하기 쉬워야 하지만 공개 화면이다. Dagster UI 를 그대로 노출하지 않고, API 가 고정 질의 3개(실행 목록·스케줄/센서·실행 로그)만 호출해 필요한 필드만 옮긴다. 실행 설정(run config)은 옮기지 않는다.
- 모든 문자열은 가림 규칙을 거친다: 인증키 파라미터, URL 비밀번호, 인증 헤더, `al_live_` 키, S3 자격증명·서명·세션 토큰, `password`·`token`·`secret` 류. `complex_key`·`stepKey` 같은 식별자는 남긴다(디버깅에 필요).
- 실패한 실행은 같은 작업·파티션이 **나중에 성공했으면 해결됨**으로 보고 기본으로 숨긴다(당시 7일: 파이프라인 실패 28건 중 23건이 재시도로 복구).
- 겪은 문제: Dagster 이벤트 로그의 시각은 **밀리초 문자열**, 실행 기록의 시각은 **초 단위 실수**다. 둘을 같은 함수로 바꾸다 연도 58705 로 계산돼 목록 전체가 500 이 났다 → 단위를 출처에서 명시적으로 바꾸고, 한 항목의 시각이 이상해도 목록은 살리도록 했다(회귀 테스트).
- `logsForRun` 은 한 번에 최대 1000개(더 크게 요청하면 GraphQL 오류) → 실패 실행 최대 40개를 동시 5개로 읽는다.

## ADR-028 ClickHouse 는 데이터 크기에 맞게 줄여 쓴다 (장애 기록)
- 겪은 문제 (2026-09-26): 웹 첫 접속·새로고침마다 모든 메뉴가 `Internal Server Error (INTERNAL)`, 기다리면 가끔 뜸.
  API 로그는 ClickHouse `MEMORY_LIMIT_EXCEEDED (241)` — 질의는 수 MB 인데 서버 전체 메모리가 상한(1.12GB)에 닿아 **시작 전에 거부**됐다.
- 원인: 기본 설정의 진단용 시스템 로그. `metric_log`(열 수천 개)·`trace_log`(477만 행)·`text_log`(trace 수준)·`asynchronous_metric_log`(3,541만 행)를 계속 쓰고,
  특히 `metric_log` 100개 조각 병합이 메모리 부족으로 **실패 → 재시도를 반복**해 한가할 때도 CPU 110~147%, 컨테이너 1.18GiB 를 잡고 있었다.
  캐시·스레드 풀 기본값(인덱스 캐시 수 GB, 스케줄 풀 512 스레드)도 서빙 데이터(수백 MB)에 비해 과했다.
- 결정: 진단 로그는 끄고(성능 측정에 쓰는 `query_log` 만 7일), 이미 쌓인 진단 표는 삭제. 캐시 상한(마크 64MB 등)과 백그라운드 풀을 데이터 크기에 맞춤.
- 결과(측정): 컨테이너 메모리 1.18GiB → 약 170MiB, 한가할 때 CPU 약 3%, 서버 메모리 추적값 862MB → 약 150MB. 재시작 뒤에도 유지.
- 재발 감지: 수집 상태 → API 연결 테스트의 서빙 DB 항목에 '메모리 사용 / 상한'을 표시 (`api_reader` 에는 `system.metrics`·`system.server_settings` 의 두 열만 추가 권한).

## ADR-029 일시 장애는 500 이 아니라 503, 화면은 자동 재시도 + 다시 시도
- 같은 장애에서 API 는 모든 ClickHouse 오류를 500 INTERNAL 로 돌려줬다 → 버그와 일시 장애를 구분할 수 없고, 화면은 오류 옆에서 로딩 틀(스켈레톤)을 계속 보여 '무한 로딩'처럼 보였다.
- 결정:
  - API: ClickHouse 연결 실패·메모리/동시성/시간 한도(241·202·159·209·210), PostgreSQL 연결·풀 대기 초과, Redis 연결 오류 → **503 `UPSTREAM_UNAVAILABLE` + `Retry-After: 2`** (어느 구성요소인지 `component`, 내부 메시지는 싣지 않음). 문법·권한 오류 같은 버그는 여전히 500 (테스트).
  - 웹: 502·503·504·네트워크 오류는 최대 2번 자동 재시도(Retry-After 존중, 최대 3초). 그래도 실패하면 원인·추적 ID와 **[다시 시도]** 버튼. 로딩 틀은 실제로 불러오는 중일 때만.
- 확인: ClickHouse 를 일부러 멈추고 지역 화면을 열면 약 3초 뒤 원인 + 다시 시도가 뜨고, 다시 켠 뒤 버튼 한 번으로 복구.

## ADR-030 API 연결 테스트는 내부 구성요소만 직접 찌른다
- 수집 상태 메뉴의 연결 테스트: ① API 서버 안에서 운영 DB·캐시·서빙 DB·Dagster 에 가장 가벼운 질의(동시, 각 2초 제한) ② 브라우저 → 웹 서버(BFF) → API 로 공개 API 8~9개를 캐시 없이 순서대로 요청해 상태 코드·지연·헤더 계약(버전 헤더 = 본문, ETag → 304, 잘못된 매개변수 4xx Problem Details, 잘못된 키 401)을 확인.
- 외부 원천(국토부·V-World)은 **호출하지 않는다**: 누구나 누를 수 있는 버튼이 일일 한도가 있는 키를 소모하게 두면 안 된다. 대신 파이프라인이 기록한 마지막 성공 수집 시각과 오늘 호출 상한 상태를 보여 준다.
- 오류는 예외 종류만 돌려준다(내부 주소·메시지 비노출), 사용자가 넣은 키는 화면 메모리에만.

## ADR-031 보안·성능 2차 점검 (측정 전후 비교)
공개 저장소로 전환하며 전체를 다시 점검했다. 찾은 것과 결정:
- **운영 API 가 익명에게 열려 있었다.** `/v1/ops/*`(오류 로그의 내부 호스트 이름·스택 경로)가 `read` 스코프라 누구나 읽을 수 있었다 → `ops` 스코프 신설(V005), 웹 BFF 키와 운영자 키에만. 익명·일반 데이터 키는 403 (테스트).
- **잘못된 키 요청은 무제한이었다.** 한도 검사 전에 401 로 끝나 키 추측·폭주를 막지 못함 → IP(해시)별 인증 실패 분당 30회 초과 시 429. 성공 요청은 세지 않아 정상 키는 영향 없음.
- **차트 툴팁 XSS.** ECharts 툴팁은 innerHTML 이라 API 가 준 시군구·시도 이름을 그대로 넣으면 원천 자료에 태그가 섞일 때 실행될 수 있었다 → `esc()` 로 이스케이프. 이 김에 툴팁의 `style` 속성을 클래스로 바꿔 **CSP 에서 `style-src 'unsafe-inline'` 제거** (브라우저 콘솔에서 위반 0 확인).
- **웹 키를 도구로 빼 쓸 수 있었다.** 키 없는 모든 요청에 웹 키를 붙였다 → 같은 출처 브라우저 요청(`Sec-Fetch-Site: same-origin`)에만. 헤더는 위조 가능하므로 문턱일 뿐이고 최종 방어선은 API 의 IP 단위 한도.
- **컨테이너:** 데이터 서비스(PostgreSQL·Redis·ClickHouse·MinIO·Trino 등)에 `no-new-privileges` 가 없었고 전체에 프로세스 수 상한이 없었다 → 12개 모두 적용(측정한 스레드 수의 약 4배, JVM·ClickHouse 는 1024). 적용 후 레이크 질의·발행 경로 정상 확인.
- **CI:** Trivy 액션 태그가 사라져 보안 잡이 실패하고 있었다 → 최신으로, 모든 액션을 커밋 SHA 로 고정(태그는 옮겨질 수 있음), 잡 시간 제한·중복 실행 취소.
- **성능:** 경계 GeoJSON(1.1MB)을 요청마다 gzip 해 201ms → 버전당 한 번 압축 4.7ms. 요청 봉투를 BaseHTTPMiddleware 에서 순수 ASGI 로 옮겨 최대 처리량 +30%(4,430 → 5,780 req/s). 정적 파일은 빌드 때 미리 압축, nginx → API 연결 재사용.
- 하지 않은 것: 이미지 다이제스트 고정(태그 + Dependabot 으로 대신), 데이터 서비스 `cap_drop: ALL`(공식 이미지 진입점이 chown·권한 전환을 해 서비스별 최소 권한 목록 검증이 필요 — 다음 과제).

## ADR-032 오류 로그 '비우기'는 삭제가 아니라 기준 시각
- 요구: 이미 확인·해결한 옛 로그가 계속 보여 새 문제와 헷갈린다 → 비우기 버튼.
- 원본을 지우면(Dagster 실행 기록·품질 검사 결과·사용량 이벤트) 감사 추적과 재현 근거가 사라지고, 각 저장소마다 삭제 권한을 API 에 줘야 한다(최소 권한 위배).
- 결정: `ops.log_view.cleared_at` 한 줄만 둔다. 그 이전 항목은 기본으로 숨기고 API 오류 요약도 그 뒤부터 센다. '비우기 이전 보기'·되돌리기 가능, 변경은 `api.audit_log` 에 남긴다. `ops` 스코프 필요 — 교차 출처 요청에는 웹 키가 붙지 않아 CSRF 로 비울 수 없다.
- 함께 한 화면 점검: 숫자 열 머리글 정렬(CSS 우선순위 버그), '더 보기' 응답이 늦게 와 다른 조건의 행이 섞이는 경쟁 조건, 키보드로 행 선택, 빈 칸의 이유 표시, 날짜 표기 통일.


## ADR-033 전체 코드 3차 점검: 조용한 실패를 없앤다
화면보다 구조·성능·보안의 안정성을 기준으로 파이프라인·API·웹·인프라 전체를 다시 읽었다. 공통된 결함은 **실패가 성공처럼 보이는 경로**였다.
- **실패한 Trino 문장이 성공으로 처리됐다.** `lake.execute()` 가 결과를 가져오는 도중의 `TrinoUserError` 를 잡아 빈 결과로 돌려줬다. Trino 는 MERGE·optimize 의 실패를 이때 알리므로 실패한 반영이 성공처럼 보일 수 있었다 → 모든 오류를 올린다. 실제 레이크 통합 테스트(MERGE·SCD2)와 유지보수 대상 표 존재를 확인했다.
- **인증키 오류가 모든 파티션을 격리했다.** 키 미등록·기간 만료·미등록 IP·미승인(포털 공통 오류 코드 20·30·31·32, 사유 없는 401·403 — 코드표에서 확인한 것만)은 파티션 탓이 아닌데 파티션마다 재시도 후 격리됐다 → `KeyRejected` 로 한도 초과(`QuotaExceeded`)처럼 **그날 실행을 멈춘다**. 수집 상태 화면은 "인증키 거부 · 키 확인 필요"로 한도 소진과 구분해 보여 준다. 요청 형식 오류(사유 10 등)는 그 파티션만 실패.
- **발행이 표 사이에서 어긋날 수 있었다.** 네 서빙 표를 하나씩 스테이징→교체해, 세 번째에서 실패하면 앞의 표만 새 달이었다 → 네 표를 모두 스테이징한 뒤에 교체하고, 스테이징 중 실패하면 스테이징만 치운다.
- **외부 API 오류 메시지에 인증키가 실릴 수 있었다.** `httpx.raise_for_status()` 의 예외 문자열에 `serviceKey=` 가 든 전체 URL 이 들어가 Dagster 실행 기록에 남는다(화면은 가리지만 원본에 남음) → `http_safe.checked()` 가 경로만 담아 올린다 (시군구·R-ONE·V-World).
- **R-ONE 이 빈 응답을 주면 기준 지수를 빈 표로 덮어썼다** → 한 건도 없으면 실패로 두고 이전 값을 유지.
- **센서 한 틱이 통째로 실패했다.** 파티션 정의 밖의 달(시험용 합성 파티션 209901)이 운영 DB 에 한 줄 있으면 알 수 없는 파티션 키로 틱 전체가 실패해 그 틱의 정상 요청까지 사라졌다 → 조회를 파티션 범위·현존 시군구로 한정. 또 5분마다 약 1.8만 행 격자 등록을 되풀이하던 것을 격자 모양이 바뀔 때만으로.
- **통합 테스트 데이터가 서비스에 노출됐다.** 통합 테스트는 실제 레이크를 쓰는데 단지 차원(`silver.apt_complex`)을 지우지 않아, 테스트 중에 돈 발행이 합성 단지 3건을 검색에 내보냈다 → 정리 범위 확대 + `gold.complex_summary` 는 공식 시군구 목록에 있는 단지만 (거래 표는 이미 발행된 달 파티션으로만 서빙). 노출된 3건은 레이크·ClickHouse·캐시에서 지웠다.
- **작업자 재시작으로 멈춘 내보내기가 영구히 한도를 막았다.** `running` 으로 남은 작업이 클라이언트당 동시 2개 제한을 계속 차지 → 30분 넘은 `running` 은 실패로 정리(1분마다), 같은 클라이언트의 동시 요청은 advisory lock 으로 한도 검사·등록을 직렬화.
- **잠정 달 판정이 UTC 기준이었다** (KST 자정~09시 사이 하루 어긋남) → KST 날짜로 통일, 두 라우터의 중복 구현을 하나로.
- **품질 파티션 응답의 `lastError` 를 가리지 않았다** → 오류 로그와 같은 비밀 가림 적용.
- **센서 틱 오류는 늘 '미해결'로 남았다** (다음 틱이 정상이어도) → 실행 실패와 같은 규칙으로, 뒤에 오류 없는 틱이 있으면 '이후 해결됨'(기본 숨김).
- **인프라:** 초기화 컨테이너(MinIO·Lakekeeper·ClickHouse 스키마·DB 마이그레이션)가 의존 서비스보다 먼저 뜨면(도커 데몬 재시작 시 관찰) 바로 실패했다 → 최대 60초 대기·재시도 (스키마 적용 자체는 재시도하지 않음). Dagster 종료 유예 10초 → 60초(SIGKILL 137 관찰). 인증 없는 Trino·Lakekeeper 의 호스트 포트를 닫았다(쓰는 곳 없음, 직접 질의는 `docker compose exec`). Grafana 는 256MB 한도에서 페이지 캐시를 계속 비우고 있어(한도 도달 8.8만 회/11분) 384MB 로.
- **웹:** 응답 캐시가 경로마다 쌓이기만 해 오래 연 탭에서 메모리가 늘었다 → 64개 상한 + 만료 항목 정리. `.env` 생성 시 비밀값을 쓰기 전에 권한을 600 으로.
- **CI:** 세 이미지(api·pipeline·web)를 실제로 빌드한다 — Dependabot 의 베이스 이미지 올림, 이미지 안의 `dbt parse` 를 병합 전에 검증.
- 하지 않은 것: Dagster UI(127.0.0.1:3600)는 인증이 없다 — 로컬 운영 도구라 두고, 공개 배포라면 앞단 인증 프록시가 필요하다 (한계에 명시). Trino 비밀번호 인증은 TLS 가 전제라 로컬 구성에서는 포트를 닫는 것으로 대신했다.

## ADR-034 백필 완료 후 확인: 모든 발행이 버전을 올린다, 일시 장애는 한 번 재시도
2021-01~2026-09 백필(시군구×월 17,664개)이 끝난 뒤 지수·단지 차원을 다시 산출하며 두 가지를 찾았다.
- **차원·지수 발행이 데이터셋 버전을 올리지 않았다.** API 결과 캐시 키와 ETag 는 버전을 포함하는데, 버전을 올리는 것은 월 발행뿐이었다. 매일 지수·단지를 새로 발행해도 다음 월 발행 전까지 브라우저는 이전 ETag 로 304 를 받아 옛 값을 보고, 서버 캐시도 최대 10분 옛 값을 줬다 → 차원·지수 발행도 버전을 올리고 입력 스냅샷(`gold.complex_summary`·`gold.price_index`)을 함께 기록한다. 확인: 지수 발행 뒤 이전 ETag 로 요청 → 304 가 아니라 200, 새 버전.
- **Docker VM 전체 메모리 부족으로 Trino 가 강제 종료됐다.** 단지 차원 재생성 중 다른 프로젝트의 프로세스가 메모리를 요청하자 커널이 VM 전체 기준으로 가장 큰 프로세스(Trino, 1.78GB)를 죽였다 (`global_oom`, Trino 자체 한도 2GB 안이었음 — 컨테이너의 OOMKilled 표시·메모리 이벤트에는 남지 않아 VM 커널 로그로 확인). Trino 는 약 1분 뒤 자동 재시작됐지만 실행은 실패로 끝나 다음 날 스케줄까지 비었다.
  → Trino·ClickHouse 를 쓰는 단계(silver 반영·dbt·발행·지수)에 **90초 뒤 1회 자동 재시도**. 이 단계들은 모두 멱등이라 다시 해도 결과가 같다. 원천 API 를 부르는 단계(bronze·시군구·R-ONE)는 호출 예산을 쓰므로 제외.
  하지 않은 것: Trino 메모리를 더 줄이기(이번 종료는 Trino 한도 초과가 아니라 VM 전체 부족), VM 메모리 늘리기(사용자 환경 설정).
- **주간 레이크 정리가 실패한 채 남아 있었다** (2026-09-27 일요일 첫 스케줄 실행, 06:32 KST 실패). bronze 는 (계약월, 시군구) 파티션이라 1.7만 개인데 한 문장으로 압축하다 Trino 의 동시 쓰기 한도에 걸렸다(`ICEBERG_TOO_MANY_OPEN_PARTITIONS`, 한도 100). 첫 표에서 멈춰 나머지 11개 표의 스냅샷 만료도 돌지 않았다.
  → 파티션이 100개 넘는 표는 파일이 2개 이상인 파티션만 `계약월 = X AND 시군구 IN (…90개)` 단위로 나눠 압축(열 사이 OR 는 Trino 가 파티션 조건으로 내려보내지 못해 쓰지 않음). 한 표가 실패해도 나머지 표는 계속하고 실패는 끝에서 모아 알린다. 분할 규칙은 단위 테스트, 실제 bronze 한 달(129개 → 90 + 39)로 확인. 다시 돌린 주간 정리: 12개 표 모두 성공(8분) — 파일 수 silver.apt_complex 2,447 → 1, silver.apt_trade 129 → 6, gold 월 표 219 → 69 (스냅샷은 스택이 3일째라 모두 7일 보존 기간 안이어서 그대로).
- **서빙 DB 한 질의의 시간 초과로 오류 로그 화면 전체가 503 이었다** (VM 메모리 부족 때 34~70초 뒤 503 5건). Dagster 가 안 될 때처럼 API 오류 부분만 빼고 안내문과 함께 200 → 운영자가 가장 필요할 때 화면이 비지 않게 (통합 테스트).
- **API 500 의 원인을 나중에 알 수 없었다.** 오류 로그의 API 5xx 는 상태 코드·지연·추적 ID 만 남기고 원인은 서버 로그에서 찾게 했는데, 컨테이너를 다시 만들면 그 로그가 사라진다 (2026-09-27 00:21 `/v1/market/ticker` 500 한 건은 그래서 원인을 확인하지 못했다 — 같은 분에 다른 요청들이 30초씩 멈췄다가 503).
  → 5xx 이면 원인 분류(예외 클래스 이름, 일시 장애는 `구성요소: 사유`)를 사용량 이벤트에 함께 남기고 오류 로그에 보여 준다. 예외 메시지는 비밀값이 섞일 수 있어 남기지 않는다 (통합 테스트: 503 `서빙 DB(ClickHouse): MEMORY_LIMIT_EXCEEDED`, 500 `ClickHouse code 62`).
- 백필 뒤 지수 검증: 비교 66개월(2021-02~2026-07)에서 R-ONE 대비 월간 변화율 상관 전국 0.916(백필 전 34개월 0.779). 가장 낮은 제주 0.512 는 비교 기간 월평균 거래가 약 200건으로 가장 적은 시도.

## ADR-035 2026-10 리뷰: 기능별 3계층, 안전망 먼저, 지원 종료 해소
계획과 우선순위는 [docs/plans/2026-10-review-plan.md](plans/2026-10-review-plan.md). 한 주제씩 작은 커밋, 리팩터링과 버그 수정은 다른 커밋, 커밋마다 린트·형식·타입·테스트 통과.
- **안전망을 먼저 깔았다.** 공개 API 의 GET 응답 36개를 골든 파일로 고정(최근 시각·추적 ID 만 정규화)하고, 웹은 서버 골든 응답으로 그린 화면 11개를 DOM 스냅숏으로, 수집 센서는 현재 계획을 테스트로 고정했다. 이후 '구조 정리(동작 변경 없음)' 커밋은 모두 이 결과가 그대로인 것으로 확인했다.
- **API 를 기능별 router·service·repository 로.** `core/`(설정·오류·응답·인증·자원), `features/<기능>/` 10개. router 는 HTTP(매개변수·스코프·캐시 헤더)만, service 는 업무 규칙만(저장소는 Protocol 로 받음 — DI 프레임워크 없이 함수 인자), repository 는 SQL 만. **의존 방향은 테스트로 강제**(`tests/test_architecture.py`: service 는 FastAPI·DB 드라이버·HTTP 클라이언트를 직접·간접으로 쓰지 않는다, 같은 기능의 adapter 를 모른다, 다른 기능은 service 로만, repository 는 HTTP 를 모른다, core 는 features 를 모른다 — 위반 4종을 넣어 실패하는지 확인). service 단위 테스트는 DB 없이 돈다.
- **수집 센서의 실행 계획도 순수 함수로** (`scheduling.py`: 우선순위·예산·진행 중·발행 전용). 센서는 상태를 읽고 RunRequest 로 바꾸기만 한다.
- **데이터 손실·보안:** 백업이 없었다 → `make backup`(PostgreSQL 덤프 3종 + raw·lake 증분 복제 + .env 사본) · `make backup-verify`(임시 PostgreSQL 에 복원해 행 수 대조). 관리 변경과 감사 기록이 다른 트랜잭션이라 '기록 없는 키 발급'이 남을 수 있었다 → 같은 트랜잭션(감사 실패 시 되돌림 테스트). silver 검사 질의에 넣는 시군구 목록을 문장 조립 직전에 다시 검증.
- **지원 종료:** ClickHouse 25.8 → 26.8 LTS(사라진 설정 하나 때문에 재시작 반복 — 테스트가 운영 설정 파일을 쓰지 않아 못 잡았다 → 테스트 컨테이너에 config.d 도 마운트), Prometheus 3.14(지원 종료) → 3.13 LTS, Trino 476 → 483(JDK 25 에서 RSS 2.08GB 로 컨테이너 한도 초과 → `MALLOC_ARENA_MAX=2`·JIT 스레드 2·힙 1.1GB, 최대 1.26GB), Python 이미지 Debian 12 → 13. 다시 놓치지 않게 주 1회 endoflife.date 점검 워크플로.
- **버그:** 같은 날 거래가 여럿이면 '최근 거래'가 엔진 병합 순서에 따라 바뀜(거래 ID 로 동점 정렬), 조건의 거래가 모두 해제면 거래 목록 500(중위가 NaN), 시장 순위가 동점일 때 질의 결과 순서에 따라 바뀜(시군구 코드 순), 레이크 통합 테스트 정리 단계의 권한 오류, 화면 스냅숏의 간헐 실패(지연 로딩 페이지를 기다리지 않음).
- **성능·신뢰성(전후 수치는 [performance.md](performance.md#2026-10-점검-브랜치-improve2026-10-review-adr-035)):** 경계 GeoJSON 직렬화·압축을 스레드로 + 워커당 한 번(첫 요청 801 → 487 ms, 그동안 다른 요청 최대 지연 409 → 129 ms). 품질 '해결됨' 판정이 `IS NOT DISTINCT FROM` 때문에 색인을 못 써 실패 1건마다 7.9만 행을 읽었다 → 파티션 있음·없음으로 나눔(446.8 → 8.6 ms, 결과 동일). 오류 로그의 출처를 동시에 읽음(장애로 한 출처가 느릴 때 합이 아니라 최댓값).
- **독립 검토(별도 에이전트, 처음 보는 사람 관점)로 찾아 고친 것:** 오류 로그에서 센서 질의만 실패해도 실행 실패 항목이 통째로 빠짐(병렬화 회귀), '동작 변경 없음' 커밋에 섞인 변화(없는 달이 든 거래 ID 500 → 404 → 이제 400), 연결 점검 API 설명 누락, 골든 비교가 정수·실수를 구분하지 못함, 모르는 지도 지표가 이름과 다른 값으로 칠해짐, 거래 조건을 빨리 바꿀 때 이전 조건의 커서로 '더 보기'(main 부터 있던 것), 대비 검사에서 빠진 쌍·칩 여백·접근성 세부, 백업의 허점(사용량 기록 미포함·완료 표시 없음·객체 수만 보는 확인·운영 값과 비교해 생기는 거짓 실패·실패 시 통과하는 실행 중 확인·절대 경로), 지원 종료 점검이 조회 실패에도 초록불, 통합 테스트가 합성 달 행을 남김(합성 달만 지우는 함수로 최소 권한 유지).
- **하지 않은 것(근거):** ClickHouse `max_threads` 조정은 벤치마크 차이가 잡음보다 작아 두었다. 전체 데이터에서 200+100 RPS 를 못 버티는 문제(9-26 의 p95 38.6 ms 는 8개월 데이터 기준)는 원인을 `region_month` 의 월 파티션(1.7만 행에 활성 파트 70개)으로 좁혔고, 승인 뒤 연 단위 파티션으로 바꿨다(ADR-037). Dagster 의 '자산마다 다른 BackfillPolicy' 경고는 이번 변경 전후 같다(선택되는 정책도 같음). 오류 로그 요청 하나가 운영 DB 연결을 최대 3개까지 동시에 쓴다(풀 10) — 운영 화면 전용이라 두었다. 웹 BFF 는 `Sec-Fetch-Site: same-origin` 이 붙은 요청에 웹 키를 붙이므로 같은 PC 의 비브라우저 프로그램은 흉내 낼 수 있다 — 포트를 127.0.0.1 에만 여는 전제(ADR-023).

## ADR-036 화면: Blueprint 색 체계 + 대비를 스크립트로 검사, 기본 테마는 OS 설정
목표는 시인성·명시성·가독성. 라이브러리를 들이지 않고 역할 토큰과 CSS 로.
- **색:** Palantir Blueprint 의 공개 색(`@blueprintjs/colors` 5.1 의 값을 그대로)으로 역할 토큰을 다시 정의했다. 이전 토큰은 보조 글자 3.8:1, 경고 3.7:1, 입력 테두리 1.5:1 등 94쌍 중 19쌍이 WCAG 기준 미달이었다. `web/scripts/contrast.mjs` 가 테마별로 글자 4.5:1·테두리·초점·스위치 3:1 을 150쌍 검사하고(`npm run lint`·`make lint`·CI), 지금은 0쌍 미달 (처음 114쌍이었는데 독립 검토가 선택 행·스위치 쌍이 빠진 것을 찾았다 — 선택 행 보조 글자 4.45:1, 어두운 테마 스위치 2.24:1 이었다). 채움(주·위험 버튼)·초점·선택 행은 별도 토큰 — 어두운 테마에서 밝은 강조색 위 흰 글자가 생기지 않게. 차트 팔레트(검증한 계열·순차·발산 색)는 그대로.
- **상승·하락 색은 국내 관례(빨강 ▲ / 파랑 ▼)를 유지**한다. 위험(빨강)과 색상이 겹치지만, 변화율은 늘 화살표·부호와 함께, 위험·경고는 글자 배지(차단·경고·미해결)로 쓰고 토큰을 분리해 두어 따로 바꿀 수 있다.
- **명시성:** 표 머리글에 단위(만원·원), 오류 수준에 기호(✕ ERROR, ! WARN), 변화율은 화면낭독기에 '상승 0.9%' 처럼 말로. 숫자는 고정폭 숫자(tabular-nums)·오른쪽 정렬.
- **조작:** 표 정렬은 머리글 안의 버튼(키보드·aria-sort, 정렬 가능한 열에 ↕), 오류 로그 줄은 펼치기 버튼, 버튼 묶음은 fieldset+숨긴 legend, 검색은 `<search>`. Biome 접근성 규칙을 모두 error 로.
- **테마:** 기본은 OS 설정을 따르고(바뀌면 따라감), 직접 고르면 기억한다. CSP 가 인라인 스크립트를 막으므로 첫 화면은 CSS `prefers-color-scheme` 로 바탕만 먼저 맞춘다. 예전 저장값은 고르지 않아도 늘 'light' 였으므로 'dark' 만 사용자의 선택으로 옮겼다.
- 확인: 모바일(375px)·데스크톱 8개 화면에서 가로 넘침 0 (화면낭독기 글자가 가로 스크롤 영역 밖으로 빠져 문서 폭을 넓히던 문제를 이 확인에서 찾아 고쳤다), 키보드로 정렬·펼치기, 밝게·어둡게 화면 확인.

## ADR-037 region_month 를 연 단위 파티션으로 (월 70개 → 연 6개)
- **배경:** `region_month`(시군구×월 통계)는 1.7만 행뿐인데 월 파티션이라 활성 파트가 70개였고, 지역 화면의 12개월 질의가 파트 약 12개를 열었다. 전체 자료 부하 시험에서 같은 구간 ClickHouse CPU 의 가장 큰 몫(92초, 거래 표 74.5초)이 이 표 질의였다.
- **측정(운영 데이터 사본, 같은 질의 600개, max_threads 2, 차례로):**

  | 구성 | 질의당 파트 | 질의당 CPU | 응답 p50 / p95 |
  |---|---|---|---|
  | 월 파티션 (이전) | 11.9 | 29.8 ms | 31 / 121 ms |
  | **연 파티션 (채택)** | 1.9 | 5.8 ms | 5 / 15 ms |
  | 파티션 없음 | 1 | 3.8 ms | 3 / 7 ms |

  파티션 없음이 조금 더 빠르지만, 연 파티션은 월 발행 한 번에 다시 쓰는 양이 그 해(≤ 약 3천 행)로 묶이고 오래된 해는 손대지 않는다.
- **발행:** 그 해의 다른 달은 지금 서빙 중인 행을 스테이징에 그대로 옮기고(옮긴 행 수 대조) 발행하는 달만 gold 에서 새로 넣어 대조한 뒤, 그 해 파티션을 `REPLACE PARTITION` 으로 원자적으로 교체한다. 다른 달을 gold 에서 다시 읽지 않는 이유: 아직 발행되지 않은 다른 달의 gold 변경이 거래 표와 어긋나게 섞여 나가지 않게. 발행은 Dagster `publish` 풀(동시 1)에서만 돌아 같은 해 두 달이 동시에 교체되지 않는다.
- **이관:** `ch-migrate` 가 파티션 키가 아직 `toYYYYMM(month)` 일 때만 `infra/clickhouse/migrate/region_month_yearly.sql` 을 한 번 실행 — 새 표에 복사 → 행 수·합계 대조(다르면 멈춤) → `EXCHANGE TABLES` → 스테이징도 같은 키로. 새 설치는 스키마 파일이 처음부터 연 파티션. 수집을 멈춘 상태에서 이관과 새 발행 코드를 함께 배포했다.
- **검증:** 실제 ClickHouse 테스트(같은 해 다른 달·다른 해 보존, 0건 달, 대조 실패 시 서빙 보존, 이관 전후 동일), 운영 이관 후 행 수·합계 동일·API 응답 8종 전후 동일, 운영 발행 1회(2026-08)에서 그 해 다른 9개월이 해시까지 그대로.
- **끝단 효과(교차 측정):** 다른 프로젝트 컨테이너가 돌던 첫 측정(호스트 부하 약 9)은 회차마다 우열이 바뀌어 결론을 못 냈다. 그 컨테이너들을 끄고 다시 재자(연·월 표를 EXCHANGE 로 맞바꿔 연·월·연·월) **네 쌍 모두 연 파티션이 앞섰다** — 120 RPS 에서 지역 통계 p95 1,130 → 251 ms, 300 RPS 목표에서 처리량 159·224 → 270·282 req/s. 목표(200+100 RPS 에서 p95 80·150 ms)는 아직 미달이고, 다음 병목은 거래 표 질의(200행 페이지에 평균 1.76만 행 읽음 — 기본 색인 간격 8,192행)다 ([측정](performance.md)).
- 같은 결정 묶음: 단지 목록의 '최근 거래'는 **해제된 거래도 포함**한다(신고된 마지막 거래 — 의도). 동작은 그대로 두고 화면 머리글에 '해제 포함'을 밝혔다.

## ADR-038 trade_current 인덱스 입도 8,192 → 1,024
- **배경:** 연 파티션(ADR-037) 뒤 300 RPS 부하에서 ClickHouse CPU 의 가장 큰 몫이 거래 표였다(trade_current 50.8 s > region_month 32.7 s). 거래 목록·요약·분포 질의 범위는 (시군구, 한 달)로 평균 153행(중앙값 100, 최대 2,006)이다. 그런데 기본 그래뉼이 8,192행이라 200행 페이지 하나에 평균 1.75만 행을 읽었다. 단지 질의(시군구 + 단지 키, 기간 없음)는 블룸 필터 단위(GRANULARITY 4 = 3.3만 행)가 넓어 52만~88만 행을 읽었다.
- **측정 1 — 차례 재생** (운영 데이터 사본 8,192·1,024·256, `system.query_log` 에 기록된 실제 API 질의, `max_threads` 2, 2회):

  | 질의 | 개수 | 질의당 읽은 행 8,192 → **1,024** (256) | 질의당 CPU 8,192 → **1,024** (256) |
  |---|---|---|---|
  | 거래 목록 200행 | 600 | 17,481 → **2,267** (744) | 6.6·7.4 → **3.7·4.3** (3.8·3.7) ms |
  | 단지 상세 거래 | 60 | 515,525 → **67,162** (20,768) | 105·116 → **34·30** (25·24) ms |
  | 단지 산점도 | 60 | 879,384 → **116,212** (36,535) | 68·67 → **37·28** (27·27) ms |
  | 지역 단지 목록 | 46 | 108,237 → **14,156** (4,554) | 46·34 → **39·13** (27·11) ms |
  | 거래 요약·분포 5종 | 830 | 8.7천~17.4천 → **1.1천~2.2천** | 차이 거의 없음 (질의당 고정 비용 약 3~4 ms) |
  | 내려받기: 시군구 5년 | 12 | 521,500 → **82,432** (37,056) | 193 → **66** (82) ms |
  | 내려받기: 전국 1년 | 9 | 514,600 (같음) | 636 → **656** (627) ms, p50 489 → 548 ms |

- **측정 2 — 동시 교차** (거래 목록 + 요약 2,400개, 동시 4·8, 두 사본을 번갈아 3회씩): **6쌍 모두 1,024 가 앞섰다.** 처리량은 동시 4 에서 466·487·428 → 544·575·469 QPS, 동시 8 에서 482·287·427 → 560·586·460 QPS 이다. 같은 일의 ClickHouse CPU 합은 13.2~20.1 → 10.0~13.5 s, 거래 목록 질의당 CPU 는 7.0~10.4 → 4.5~6.4 ms 로 줄었다. 요약 질의는 비슷했다.
- **256 이 아닌 이유:** 1,024 보다 나은 곳은 단지 질의(약 20%)뿐이고 거래 목록·요약은 같다. 대신 마크 4배(2,697 → 10,572), 디스크 179 → 199 MB, 기본키 메모리 225 → 559 KB 가 들고, 시군구 5년 내려받기는 오히려 느렸다(66 → 82 ms).
- **비용:** 마크 398 → 2,699, 디스크 159 → 179 MB, 기본키 메모리는 그대로(약 225 KB). 전국 1년 내려받기(51만 행)는 읽는 양이 같고 CPU 차이 3% 안이다. 응답 p50 은 12% 늘었다(9회 측정이라 잡음과 구분되지 않음). 내려받기는 비동기 작업이다.
- **이관:** `ch-migrate` 는 입도가 1,024 가 아닐 때만 `infra/clickhouse/migrate/trade_current_granularity.sql` 을 실행한다. 순서는 스테이징 DROP → 새 표 복사 → (행 수, 행 체크섬) 대조(다르면 멈춤) → `EXCHANGE TABLES` → 스테이징을 새 입도로 다시 만들기다. 스테이징 파트는 `REPLACE PARTITION` 으로 그대로 붙으므로 스테이징도 같은 입도여야 한다. 스테이징을 먼저 지우는 이유는 수집 중에 배포해도 그사이 발행이 실패하고 `needs_publish` 로 다시 발행되게 하기 위해서다. 이관이 실패하면 스키마를 다시 적용해 스테이징을 되살린다.
- **독립 검토가 찾은 구멍(고침):** 발행이 대조를 마친 뒤 교체하기 전에 이관이 통째로 끝나는 경우가 있다. 그러면 새로 만든 **빈** 스테이징으로 교체해 그 달이 지워진다. region_month 는 그 해 파티션째 DROP 된다. 그런데 발행은 성공으로 남는다. 그래서 교체 직전에 네 표 모두 스테이징 행 수를 다시 세고(연 파티션은 같은 해 다른 달 복사분까지), 대조 때와 다르면 하나도 교체하지 않게 했다. 남는 창은 표 교체 사이 수 ms 뿐이고, 그때 실패해도 재시도·재발행으로 복구된다.
- **운영 적용 (2026-10-03 23:24 KST):** 진행 중 실행이 0건인 것을 확인하고 배포했다. 이관에 13초가 걸렸다. 행 2,688,294건과 행 체크섬이 같았고, 표와 스테이징 모두 1,024, 블룸 필터도 유지됐다. 거래 표를 읽는 API 응답 20개(거래 목록·커서 다음 쪽·분포·단지 목록·단지 상세)가 이관 전후로 바이트 단위까지 같았다.
- **끝단(k6) 전후 — 결론 불가:** 질의당 읽은 행은 1.32만 → 1.73천(−87%)으로 줄었다. 그러나 이관 뒤 8회 중 3회는 바꾸지 않은 region_month 응답까지 크게 느려졌다(호스트 부하 2.7~8.9). 그래서 회차 차이가 표 구성보다 기계 상태에서 왔다. 300 RPS 처리량은 전 275·277 / 후 230·266·288·269 req/s 다. 운영 표를 맞바꾸는 교차 측정은 수집을 멈춰야 해서 하지 않았고, 측정 2 로 대신했다 ([측정](performance.md)).
- **한계:** NFR-04 목표(200+100 RPS 에서 p95 80·150 ms)는 여전히 미달이다. 300 RPS 에서는 API(약 0.85코어)·ClickHouse(약 1.3코어)·k6 가 5코어 VM 을 나눠 쓴다. 그래서 질의 비용이 줄어도 끝단 지연으로 곧바로 이어지지 않는다.

## ADR-039 2026-10 출시 기준 QA: 결함 16건과 그에 따른 결정
- **방법:** 운영 스택과 완전히 분리한 QA 스택(`aptlake-qa`, 운영 규모 생성 데이터 270만 건·조작 문자열)과 Testcontainers 에서만 시험했다. 결함마다 번호를 붙인 실패 시험을 먼저 커밋하고 근본 원인을 고쳤다(같은 시험 통과). 결과·증거는 [QA 보고서](qa/2026-10-qa-report.md).
- **권한 — 보기와 쓰기를 나눈다(QA-001):** 웹 BFF 키가 `ops` 전체 권한이라, 공개 웹에서 누구나(브라우저 밖에서도 `Sec-Fetch-Site` 헤더 한 줄로) 오류 로그를 비우고 되돌릴 수 있었다. ADR-031 의 "ops 는 익명에게 막는다"가 공개 진입점에서는 지켜지지 않았다.
  - 사용자 결정에 따라 읽기 전용 `ops_read` 를 두었다(V008). 웹 키는 `read`·`ops_read` 만 갖는다.
  - 수집 상태 보기는 공개로 두고, 비우기·되돌리기는 `ops`(운영자 키)만 한다. 화면은 확인 줄에서 운영자 키를 받아 그 요청에만 붙인다.
- **DB 대기에 상한(QA-007·008):** 응답 없는 ClickHouse 를 클라이언트 기본 300초까지, PostgreSQL 잠금을 무기한 기다렸다.
  - ClickHouse 는 연결 3초·응답 10초(서버 질의 상한 5초 + 여유), PostgreSQL 은 `statement_timeout` 5초·`lock_timeout` 2초를 둔다. 넘으면 기존 일시 장애 경로(503 + Retry-After)로 끝낸다.
  - 서버 프로세스 자체가 멈춘 경우 PostgreSQL 은 서버가 상한을 집행하지 못한다(남는 한계).
- **대량 내보내기는 디스크 정렬(QA-006):** 전국 전체 기간(255만 행)이 exporter 메모리 상한(400MB)에서 `MEMORY_LIMIT_EXCEEDED` 로 실패했고, 데이터가 늘수록 내보낼 수 있는 기간이 줄고 있었다.
  - `max_bytes_before_external_sort` 150MB 를 둔다. 26.8 은 비율 설정(`max_bytes_ratio_before_external_sort`, 기본 0.5)이 있으면 바이트 값이 쓰이지 않아 비율을 0 으로 끈다.
  - 결과는 270만 행에서 최대 216MB·3.9초다.
- **같은 출처의 외부 스크립트는 고정 + SRI(QA-004):** `/docs` 의 Swagger UI 를 `swagger-ui-dist@5`(움직이는 버전)에서 5.33.1 로 고정하고 sha384 무결성을 건다. 버전을 올리는 절차는 runbook 에 있다.
- **화면은 데이터보다 자리를 먼저(QA-013):** 데이터가 늦게 오며 화면이 크게 밀렸다(CLS 0.21~0.83).
  - 지표 띠·요약 줄·기간 선택기는 같은 구조로 미리 그리고, 본문은 최소 높이를 화면 높이로 둔다.
  - 좁은 화면의 지역 선택기는 한 줄을 다 쓴다. 이렇게 해서 CLS 0.04 이하가 됐다.
- **접근성 기준(QA-010·011·014·016):** 실제 Chrome 의 axe WCAG 2.1 AA 와 Lighthouse 를 QA 점검 스크립트로 둔다(`qa/probes/`).
  - 글 속 링크는 밑줄을 친다.
  - 스크롤 영역은 초점을 받는다(Biome 규칙과 충돌하는 곳은 이유를 적은 예외 주석).
  - 보이는 글자를 접근 가능한 이름에 넣는다.
  - 팝업을 Esc 로 닫으면 연 버튼으로 초점을 돌린다.
- **고치지 않은 것:**
  - QA-005: 이미지 안의 수정판 있는 HIGH·CRITICAL 취약점(Debian pcre2, `psycopg-binary` 휠이 묶어 온 pcre2 10.32·OpenSSL 1.1.1k, 서드파티 이미지)과 CI 의 이미지 스캔 부재. 기반 이미지 갱신·Trivy 이미지 스캔·`psycopg[c]` 검토를 권고한다.
  - QA-009: NFR-04 성능 목표 미달. 가상 머신 CPU 를 k6·API·ClickHouse 가 나눠 쓰는 환경에서 측정 수치로 기록했다.
