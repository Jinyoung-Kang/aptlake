# 데이터 제품 기능 명세서 — 변경분 피드 · 버전 스냅숏 내보내기 · 원천 반영 지연 · 플랜과 사용량

상태: **초안 (승인 전)** · 작성 기준 커밋 `4d45c86` · 짝 문서: [설계 계획서](2026-10-data-product-design.md)

## 0. 왜 만드는가

AptLake 의 자리는 "앱을 만드는 사람을 위한, 검증 기록이 붙은 실거래 데이터 API" 다. 무료 원천(국토부 실거래 API)과 앱 사이에서
고유 ID·변경 이력·품질 검사·버전을 붙여 파는 B2B 데이터 구독으로 설명한다 (포트폴리오용, 실제 상용화는 하지 않음).
이 문서의 네 기능은 그 설명을 제품에서 확인할 수 있게 하는 최소 단위다.

| # | 기능 | 누가 쓰나 | 한 줄 |
|---|---|---|---|
| F2 | 변경분 피드 | 데이터를 자기 DB 에 맞춰 두는 기업 고객 | 지난 버전 이후 바뀐 거래만 받는다 |
| F3 | 버전 스냅숏 내보내기 | 결과를 다시 내야 하는 연구자·기관 | 과거 발행 버전 그대로의 거래 데이터를 받는다 |
| F4 | 원천 반영 지연 | 데이터를 믿고 쓸지 판단하는 모든 사용자 | 계약·해제가 서비스에 들어오기까지 걸린 시간을 공개한다 |
| F5 | 플랜·사용량·청구 단위 | API 사용자 | 내 한도·사용량·과금 대상 단위를 한 화면에서 본다 |

## 1. 공통 규칙

- **추측 값 금지 (ADR-018):** 원천·측정·결정적 계산으로 나온 값만 응답과 화면에 쓴다. 가격(원)은 근거가 없으므로 쓰지 않는다 (F5).
- **응답 형식:** 지금과 같다 — 본문에 `datasetVersion`·`dataAsOf`, 헤더에 `X-Dataset-Version`·`X-Data-As-Of`, 오류는 RFC 9457 Problem Details(`code`·`traceId`).
- **이름:** 경로는 `/v1/...`, 매개변수와 응답 필드는 camelCase, 오류 코드는 `UPPER_SNAKE`.
- **스코프·플랜:** 모든 라우트는 `require_scope` 를 선언한다 (기동 검사). 거래 단위 레코드를 돌려주면 그 수만큼 하루 행 한도에서 뺀다 (ADR-024).
- **데이터셋 버전:** `gold@YYYY-MM-DD.n` (발행 때마다 하나). 버전 사이의 순서는 문자열이 아니라 **발행 시각**(`published_at`)으로 정한다 — `.10` 부터 문자열 순서가 틀린다.
- **기능 시작 전 버전:** 이 기능들은 배포 뒤 발행부터 기록을 남긴다. 그 전 버전은 F2·F3 에서 "기록 없음"으로 답한다 (지어내지 않는다).

## 2. F2 변경분 피드

### 2.1 사용자 이야기
- 고객은 처음에 전체를 한 번 받고(F3), 그 뒤로는 하루 한 번 "지난번 받은 버전 이후 바뀐 것"만 받아 자기 DB 를 맞춘다.
- 해제·등기일 채움처럼 원천이 나중에 바꾼 값, 새로 신고된 거래, 원천에서 사라진 거래를 모두 놓치지 않아야 한다.

### 2.2 범위
- 대상: 거래(`trade_current` 와 같은 열). 단지·지역 통계·지수는 대상이 아니다.
- 비목표: 실시간 푸시(웹훅), 열 단위 부분 갱신 형식, 사라진 거래의 영구 삭제.

### 2.3 API
`GET /v1/trades/changes?since=<datasetVersion>[&limit=][&cursor=]` — 스코프 `bulk`, 플랜 `allow_bulk`(지금은 pro)

| 매개변수 | 필수 | 규칙 |
|---|---|---|
| `since` | 첫 페이지 | 고객이 마지막으로 반영한 버전. 이 버전 **다음** 발행부터 돌려준다 |
| `limit` | 아니오 | 1 ~ 플랜 `max_page_size`, 기본 = 플랜 `max_page_size` |
| `cursor` | 둘째 페이지부터 | 이전 응답의 `page.nextCursor`. `since`·상한 버전·`limit` 에 묶여 서명된다 |

응답 (필드 모양 예시):
```json
{
  "datasetVersion": "gold@…",
  "dataAsOf": "…",
  "fromVersion": "gold@…(since)",
  "toVersion": "gold@…(첫 페이지 시점의 최신 발행)",
  "items": [
    {
      "publishedVersion": "gold@…",
      "change": "updated",
      "tradeId": "41135-202606-…-1",
      "changedFields": ["cancelled", "cancelDate"],
      "trade": { "…": "trade_current 와 같은 필드 (removed 면 null)" }
    }
  ],
  "page": { "nextCursor": "…또는 null" }
}
```

### 2.4 변경 종류 — 발행 직전 서빙 값과 새 값의 비교로 정한다

| `change` | 조건 (같은 거래 ID 기준, 그 달 파티션 안) |
|---|---|
| `added` | 새 값에만 있다 |
| `removed` | 이전 값에만 있다 (예: 같은 지문 묶음 안 순서가 바뀌어 ID 가 달라진 경우, 지문 재료가 정정된 경우) |
| `updated` | 둘 다 있고 서빙 열 하나 이상이 다르다 — 원천 값 변경(버전 증가), 이상치 표시(`isOutlier`) 변화 포함 |
| `missing` | `missingSince` 가 비어 있다가 채워졌다 (원천에서 사라짐 — 삭제하지 않고 표시만) |
| `restored` | `missingSince` 가 채워져 있다가 비었다 |

- `changedFields` 는 `updated` 일 때만, 응답 필드 이름으로 준다.
- 한 발행 안에서 한 거래는 한 항목만 나온다. 여러 발행에 걸치면 발행마다 하나씩 나온다 (마지막 것이 최신 상태).

### 2.5 동작 규칙
- **일관성:** 상한 버전(`toVersion`)은 첫 페이지에서 정해 커서에 넣는다. 페이지를 넘기는 동안 새 발행이 있어도 결과가 흔들리지 않는다. 고객은 마지막 페이지 뒤 `toVersion` 을 다음 `since` 로 쓴다.
- **정렬:** (발행 시각, 거래 ID) 오름차순. 같은 요청이면 같은 결과다.
- **보존:** 변경 기록은 **설정값 기간**(제안 90일) 동안만 둔다. `since` 가 보존 기간보다 오래됐거나 기능 시작 전 버전이면 **410 `CHANGES_EXPIRED`** — 본문에 "스냅숏 내보내기(F3)로 다시 받은 뒤 그 버전부터 이어 받으라"는 안내와 이어 받을 수 있는 가장 오래된 버전을 넣는다.
- **없는 버전:** `since` 가 발행 기록에 없으면 404 `VERSION_NOT_FOUND`. `since` 가 최신이면 200 + 빈 `items`.
- **발행 실패:** 버전 기록까지 끝난 발행의 변경만 보인다. 중간에 실패한 발행의 변경은 보이지 않고, 잃지도 않는다 —
  비교 기준이 '마지막으로 기록된 발행'이라, 서빙 교체 뒤 기록만 실패했어도 그 변경은 다음 발행에 함께 나온다.

### 2.6 권한·한도
- `bulk` 스코프 + `allow_bulk` 플랜. 아니면 403 (`PLAN_NOT_ALLOWED`, 내보내기와 같은 코드).
- 돌려준 항목 수만큼 하루 행 한도에서 뺀다. 분당 요청 한도는 공통.
- 커서 변조·다른 조건 재사용은 400 `INVALID_CURSOR` (지금 거래 목록과 같다).

### 2.7 수용 기준
1. 한 달을 다시 발행하면 그 사이 바뀐 거래 수 = 피드 항목 수이고, 종류별 수가 직접 비교한 값과 같다 (시험 데이터: 추가·해제·사라짐·복귀·ID 변경 각 1건 이상).
2. `since` 부터 모든 페이지를 받아 순서대로 적용하면 고객 쪽 표가 `toVersion` 의 `trade_current` 와 행·값까지 같다.
3. 발행이 교체 전에 실패하면 그 변경은 피드에 나오지 않는다. 교체 뒤 버전 기록만 실패하면 그 변경이 다음 발행에 빠짐없이 나온다.
4. 페이지를 넘기는 중에 새 발행이 생겨도 결과가 바뀌지 않는다.
5. 보존 기간 밖 `since` 는 410, 없는 버전은 404, bulk 아닌 키는 403.
6. 응답 지연 p95 를 QA 스택에서 재고 성능 문서에 남긴다 (목표값은 측정 후 정한다).

## 3. F3 버전 스냅숏 내보내기

### 3.1 사용자 이야기
- 연구자가 "`gold@…` 버전의 서울 2025년 거래"로 분석했다면, 나중에 누구든 같은 버전을 지정해 **같은 행**을 받을 수 있어야 한다.
- F2 를 처음 시작할 때 기준이 되는 전체 데이터를 받는다.

### 3.2 범위
- 지금 내보내기(`POST /v1/exports`, Parquet)에 `datasetVersion` 을 더한다. 생략하면 최신 버전.
- 비목표: 기능 시작 전 버전 복원, CSV 등 다른 형식, 지역 통계·지수의 버전 스냅숏.

### 3.3 API 변경
- `POST /v1/exports` 본문(또는 매개변수)에 `datasetVersion` (선택) 추가. 다른 조건(`sggCd`·`from`·`to`·`includeCancelled`)은 지금과 같다.
- `GET /v1/exports/{jobId}` 응답에 추가: `datasetVersion`, `sha256`(결과 파일), `expiresAt`.
  - 상태에 `expired` 추가: 결과 파일 보관(1일)이 지나면 다운로드 주소 대신 `expired` (지금은 지워진 파일 주소를 준다 — 6장 D3).
- 오류:
  - 기록에 없는 버전 404 `VERSION_NOT_FOUND`
  - 보관 기간이 지났거나 기능 시작 전 버전 410 `SNAPSHOT_EXPIRED` (이용 가능한 가장 오래된 버전 안내)

### 3.4 동작 규칙
- 결과의 행은 그 버전 시점에 서빙하던 `trade_current` 와 같다. 열 구성(21개)은 지금 내보내기와 같다.
- 같은 버전·같은 조건이면 같은 행·같은 순서(`deal_date`, `trade_id`). 파일 해시가 같은지는 시험으로 확인하고, 확인된 범위만 문서에 쓴다.
- 스냅숏 보관: 설정값 정책(제안 — 최근 N일의 모든 버전 + 달마다 마지막 버전 1년). **N 과 용량은 첫 단계에서 실측한 뒤 정한다.**
- 권한·한도는 지금 내보내기와 같다 (`bulk` + `allow_bulk`, 고객당 동시 2건).

### 3.5 수용 기준
1. 버전 V 로 내보낸 행 집합 = V 가 최신이던 때 `trade_current` 를 같은 조건으로 조회한 결과 (시험에서 V 직후에 떠 둔 기준값과 비교).
2. V 이후 발행이 여러 번 있어도 1 이 유지된다.
3. F2 와 이어진다: V 스냅숏 + `since=V` 피드 적용 = 최신 `trade_current`.
4. 만료된 작업은 `expired`, 보관 밖 버전은 410.

## 4. F4 원천 반영 지연

### 4.1 사용자 이야기
- "어제 계약이 오늘 보이나?", "해제는 얼마 만에 반영되나?"를 숫자로 보고 데이터를 쓸지 판단한다.

### 4.2 지표 (분포로 보여 준다 — L1·L2 는 일, L3 은 분 단위)

| 지표 | 정의 | 출처 |
|---|---|---|
| L1 신고 반영 | 거래가 처음 관측된 날 − 계약일 | silver 버전 1 의 `valid_from`(수집 시각) |
| L2 해제 반영 | 해제가 처음 관측된 날 − 해제일 | `is_cancelled` 가 처음 참인 버전의 `valid_from` |
| L3 수집→발행 | 그 수집분이 서빙에 발행된 시각 − 수집 시각 | 발행 때 남기는 기록 (기능 시작 후부터) |

- L1·L2 는 원천 쪽 지연(신고·공개)에 우리 수집 주기가 더해진 값이다. 화면에 그렇게 쓴다.
- **측정 해상도:** 다시 받는 주기 = 계약월이 3개월 이내면 매일, 12개월 이내면 30일, 그 밖은 90일 (`ops_db.next_due`). 그래서 L1·L2 는 **관측 때 계약월이 3개월 이내였던 것만** 분포에 넣는다. 나머지는 건수만 따로 보인다.
- **제외 (중도 절단):** 파티션의 첫 수집(초기 적재·백필)에서 이미 있던 거래와 해제는 "언제부터 있었는지" 모르므로 뺀다. 그래서 측정은 2026-09-28 백필 완료 뒤 관측분부터 쌓이고, 화면에 측정 시작일과 표본 수 `n` 을 함께 보인다.
- 시각 순서가 뒤집힌 버전(6장 D1)은 고칠 때까지 빼고 그 수를 보인다.

### 4.3 API·화면
- `GET /v1/quality/latency?from=YYYY-MM-DD&to=YYYY-MM-DD[&sido=]` (스코프 `read`, 행 차감 없음)
  - 지표별로 `n`, 제외 수(사유별), p50·p90·p99, 구간 분포, 측정 시작일을 준다 (L1·L2 일, L3 분).
- 데이터 품질 화면에 "원천 반영 지연" 구역을 더한다.
  - 지표 3개의 중앙값·p90 과 `n`
  - 분포 막대 (지표 하나씩)
  - 해상도·제외 규칙 설명
  - 표 보기

### 4.4 수용 기준
1. 시험 데이터(수집 시각을 정해 둔 버전들)로 계산한 분위수가 손으로 계산한 값과 같다.
2. 첫 수집분·해상도 밖·시각 역전 버전이 규칙대로 빠지고 사유별 수가 맞다.
3. 표본이 0이면 "측정 중" 상태와 측정 시작일만 보이고 숫자는 보이지 않는다.

## 5. F5 플랜·사용량·청구 단위

### 5.1 사용자 이야기
- 개발자가 키를 넣으면 내 플랜 한도, 오늘 남은 행, 최근 사용 추이, 달마다 과금 대상이 될 단위를 한 화면에서 본다.

### 5.2 범위
- 가격(원)은 보이지 않는다. 근거 있는 단가가 없어서다 (ADR-018). "청구 단위"는 실제로 센 값만 쓴다.
- 비목표: 결제, 플랜 변경 신청, 청구서 발행.

### 5.3 API
- `GET /v1/plans` (스코프 `read`, 익명 가능): 공개 플랜(anonymous·free·pro)의 한도 전부 — 분당 요청, 하루 행, 조회 기간, 페이지 크기, 대량 내보내기·피드 가능 여부.
  - 웹에 고정해 둔 플랜 표를 이 응답으로 바꾼다 (값의 출처를 하나로).
- `GET /v1/me/usage` 응답에 더한다 (키 필요):
  - `limits`: 플랜 한도 전부
  - `today`: **이 키** 기준 오늘 사용한 행·남은 행 (한도를 세는 단위와 같은 값)
- `GET /v1/me/usage/monthly?months=1..6` (키 필요): **이 고객(모든 키 합)** 의 달별 요청 수, 오류 수, 과금 대상 행 수, 한도 초과(429) 수, 내보내기 건수·행 수.

### 5.4 화면 (개발자)
- 플랜 비교 표 (`/v1/plans`)
- 내 키: 오늘 행 사용률 막대(이 키 기준), 최근 30일 일별 요청·행(고객 기준), 달별 청구 단위 표
- 기준이 다른 숫자(키 기준 / 고객 기준)는 이름표로 나눈다.

### 5.5 수용 기준
1. 시험 키로 거래 목록 n행을 받으면 `today.rowsUsed` 와 이번 달 과금 대상 행이 n 늘어난다. 304 응답은 늘지 않는다.
2. 내보내기 1건(m행)이 달별 내보내기 행 수에 m 으로 잡힌다.
3. 웹에 플랜 숫자가 코드로 박혀 있지 않다 (시험으로 확인).
