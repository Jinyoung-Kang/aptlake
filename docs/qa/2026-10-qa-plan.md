# AptLake 출시 기준 QA 계획 (2026-10)

브랜치 `qa/2026-10-release` (main d70042c 에서 분기). 이 문서를 승인받은 뒤부터 끝까지 진행한다.

## 1. 목적과 작업 규칙
- 목적: 결함을 찾아 **실패하는 시험으로 재현·증명**한 뒤, 근본 원인을 고쳐 **같은 시험이 통과**하게 한다.
- **새로 추가하는 파일**은 테스트 코드, 테스트 데이터, 점검 스크립트(`qa/`)와 QA 문서(이 계획·결과 보고서)뿐이다.
  - 제품 코드는 확인된 결함의 근본 원인을 고칠 때만 최소한으로 바꾼다. 리팩터링·기능 추가는 하지 않는다.
- 결함 하나에 커밋 둘: ① 결함 번호를 붙인 실패 시험 → ② 수정(같은 시험 통과).
  - 고치지 않기로 한 결함(사용자 판단 필요·인프라 영역)은 `xfail(strict=True, reason="QA-0NN …")` 로 남긴다. 그러면 전체 시험은 초록으로 유지되면서 결함은 기록에 남는다.
- 추측으로 결함을 적지 않는다. 재현되지 않은 의심은 **미확인**으로 따로 적는다.
- 계층 위반·순환 의존 같은 구조 문제는 결함과 분리해 **개선 제안**으로 적는다.
- 치명적 보안 결함이나 데이터 손실 결함은 발견 즉시 알리고 계속 진행한다.

## 2. 시험 환경 — 운영 스택과 완전히 분리
지금 로컬에서 도는 `aptlake` 스택이 이 프로젝트의 운영 환경이다.
- 들어 있는 것: 3일치 원천 호출 한도로 수집한 실제 레이크, 실제 키, ops DB.
- **이 스택에는 시험 요청을 보내지 않는다.** 운영 스택에 쓰는 기존 `make test-integration`, `make loadtest` 도 실행하지 않는다.

| 환경 | 구성 | 용도 |
|---|---|---|
| Testcontainers | 기존 API·파이프라인 시험 방식 (PostgreSQL·Redis·ClickHouse 26.8 임시 기동, 운영과 같은 마이그레이션·사용자·서버 설정) | 회귀, 결함 재현 시험, 장애 주입 단위 시험 |
| **QA 스택** `aptlake-qa` | `qa/docker-compose.qa.yml` override, 서빙 계층만 (postgres·redis·clickhouse·minio·db/ch-migrate·api·api-internal·web) | 브라우저 화면, 보안, 신뢰성(장애·재시작·동시성), 부하, Lighthouse·접근성, 백업·복원 |
| QA 레이크 (필요할 때만) | 같은 override 에 lake 프로필 (minio·lakekeeper·trino) | 파이프라인 SCD2 통합 시험. QA 서빙 스택을 내린 뒤에만 띄운다 (메모리) |

- **QA 스택 분리:** 운영 compose 는 서브넷 172.30.61.0/24, 이미지 태그 `aptlake-*:local`, 포트가 고정이다. 그래서 override 에서 아래를 모두 바꾼다.
  - 프로젝트 이름 `aptlake-qa` (볼륨·네트워크 이름이 달라짐)
  - 서브넷 172.30.71.0/24
  - 이미지 태그 `aptlake-qa-*:local` (운영 이미지를 덮어쓰지 않게)
  - 포트 +100 (웹 3710, API 8710, 내부 8711, ClickHouse 8740, PostgreSQL 5592, Redis 6539, MinIO 9700/9701)
  - 비밀값은 QA 전용 무작위 값 `qa/.env.qa` (git 제외). 외부 API 키는 넣지 않는다 (수집 안 함).
- **메모리:** 운영 스택이 4.1 GB 를 쓰고 VM 은 7.75 GB 다. QA 서빙 스택(약 1.5 GB)은 함께 띄운다. QA 레이크(Trino 2 GB)는 QA 서빙 스택을 내린 뒤 띄운다. 무거운 단계 전에는 `docker stats` 로 여유를 확인한다 (ADR-034).
- **시험 데이터 (생성):**
  - 기능용 소형 데이터: 정해진 값과 경계 사례 — 해제·이상치·NULL 층·면적 0·한글/이모지/긴 단지명·`<script>`·`'; DROP` 같은 조작 문자열이 든 단지명, 거래 0건 달, 경계 날짜.
  - 성능용 대형 데이터: 운영과 같은 모양과 규모 — 시군구 256 × 70개월, 거래 약 270만 건, 집계·지수·경계 도형·품질 격자.
  - 키·계정은 QA 스택의 관리 API 로 새로 만든다.
- **외부 API:** 원천(국토부·행안부·R-ONE·V-World)은 호출하지 않는다. 저장된 응답(`pipeline/tests/fixtures`)과 목으로만 검증한다.
- **설치할 점검 도구** (모두 스크래치 디렉터리·QA 전용 컨테이너):
  - k6 (이미 있음), Lighthouse·axe-core (npm), toxiproxy (지연·끊김 주입), Trivy (이미지 취약점), gitleaks (비밀 스캔)

## 3. 현황 파악 결과
- **기능·데이터 흐름:** 원천 수집(RTMS·행안부·R-ONE·V-World) → bronze → silver(SCD2) → gold(dbt) → ClickHouse 발행(스테이징 + REPLACE PARTITION, 데이터셋 버전) → API(Redis 결과 캐시·한도) → 웹(nginx BFF 가 웹 키를 붙임)
- **공개 API 25경로** (8610):
  - 시장: `market/overview` · `ticker`
  - 지역: `regions` · `months` · `distribution` · `complexes`
  - 거래: `trades` (커서) · `history`
  - 단지·검색: `complexes/{key}` · `search`
  - 지수·경계: `index` · `index/summary` · `geo/sgg`
  - 품질: `quality/summary` · `partitions` · `partition 상세` · `rollup`
  - 운영(ops 스코프): `status` · `errors` · `errors/clear` POST/DELETE · `connectivity`
  - 내보내기(bulk 스코프): `exports` POST · `exports/{jobId}`
  - 사용량: `me/usage`
  - 그 밖: `/healthz` · `/readyz` · `/openapi.json` · `/docs`
- **내부 API 4경로** (8611, 관리 스코프): 클라이언트 생성, 키 발급, 키 폐기, 파티션 재시도
- **권한:**
  - 키는 `al_live_<id>.<secret>` 형식이고 HMAC 으로 저장한다. 스코프는 read·bulk·admin·ops, 플랜별로 분당 한도·일일 한도·기간·페이지 크기가 다르다.
  - **웹 BFF 키는 read·ops 권한**이다 (ADR-031). nginx 가 `Sec-Fetch-Site: same-origin` 요청에만 이 키를 붙인다.
- **화면 8개** (단일 페이지 앱, 해시 라우팅): 시장 개요 · 지역 분석 · 거래 목록 · 가격지수 · 단지 · 데이터 품질 · 개발자(키 입력·연결 테스트) · 수집 상태(오류 로그 비우기·되돌리기). 테마는 밝게·어둡게·OS 를 따른다.
- **기존 시험 313개:** 파이프라인 77 (단위 75 + 운영 레이크 통합 2), API 141 (단위 68 + Testcontainers 통합 73, 응답 골든 36), 웹 73 (Vitest, 화면 스냅숏 11), dbt 22 (레이크에서 월마다).
  - 그 밖에 lint(ruff·mypy·tsc·Biome·색 대비), audit(pip-audit·npm audit), CI 7개 작업(이미지 빌드·gitleaks·Trivy·compose 검증 포함)이 돈다.
- **빌드·실행:**
  - `make up` (전체), `make serve` (서빙)
  - `make test-pipeline` · `make test-api` · `make test-web` · `make lint` · `make audit`
  - 배포: `docker compose up -d --build api api-internal web`, `make pipeline-redeploy`

## 4. 위험 순서와 검증 항목
위험이 큰 순서로 진행한다. 각 항목은 **가설**이고, 재현되면 결함으로, 재현되지 않으면 '확인됨(문제 없음)' 또는 '미확인'으로 적는다.

### 4.1 보안 (최우선)
- **S1 권한 상승:** 익명 요청이 `Sec-Fetch-Site: same-origin` 헤더 하나로 BFF 의 웹 키(ops 권한)를 얻는가?
  - 확인할 결과: 내부 오류 로그 열람, 로그 비우기·되돌리기, 연결 점검.
  - 화면이 이 권한을 쓰는 것이 설계상 의도인지 코드·ADR 로 판단이 안 되면, 그 부분만 질문한다.
- **S2 인가 누락(IDOR):** 다른 클라이언트의 내보내기 `jobId`·서명 URL·사용량에 접근할 수 있는가? 폐기된 키·만료 키·스코프 없는 키가 막히는가? 관리 경로가 BFF·공개 앱에서 경로 변형으로 우회되는가?
  - 변형 예: `//`, `%2F`, 대소문자, `..`, 끝 `/`
- **S3 인젝션:** 모든 질의·경로·본문 매개변수와 커서·`tradeId`·`complexKey`·검색어를 조작한다 (SQL·LIKE 와일드카드·널 바이트·유니코드·아주 긴 값). 확인할 것은 ClickHouse·PostgreSQL 질의 결과, 오류 응답, 지연이다.
- **S4 XSS·CSP:** 조작된 단지명·지역명이 화면(표·차트 툴팁·지도·검색 결과)에서 실행되는가? 웹·API 의 보안 헤더와 CORS, `/docs` 의 완화된 CSP(jsdelivr·unsafe-inline)도 본다.
- **S5 한도 우회:** `X-Forwarded-For` 위조, 웹 플랜 IP별 한도, 인증 실패 IP별 제한, 키 존재 여부가 응답 시간으로 드러나는지, 동시 요청으로 분당·일일 한도를 넘길 수 있는지 본다.
- **S6 비밀값 노출:** 저장소 이력(gitleaks), 이미지 레이어, 컨테이너 로그, 오류 응답·서명 URL·Dagster/Grafana/MinIO 기본 자격 증명, 웹 번들에 키가 남는지 본다.
- **S7 지원 종료·취약 버전:** `tools/check_eol.py`, pip-audit·npm audit, QA 이미지 Trivy 스캔.

### 4.2 데이터 손실·오염
- **D1 발행 원자성:** 네 표를 교체하는 도중 프로세스가 죽거나 ClickHouse 가 끊기면 표끼리 어긋나는가? 그때 데이터셋 버전·`needs_publish` 는 어떻게 되는가? (Testcontainers 로 강제 중단)
- **D2 백업·복원:** QA 스택에서 `make backup` → `make backup-verify` 로 실제 복원까지 한다. 범위는 PostgreSQL 3개 DB·MinIO·사용량 기록이다.
- **D3 운영 로그·감사:** 비우기·되돌리기를 동시에 하거나 거듭 할 때 상태와 `audit_log` 가 맞는가?
- **D4 내보내기 생명주기:** 작업자 재시작, 만료 정리, 같은 요청 중복이 다른 클라이언트의 객체·작업을 건드리는가?
- **D5 사용량 기록:** ClickHouse 가 멈춘 동안 사용량 이벤트가 사라지는가? 한도·일일 한도 계산이 틀어지는가?
- **D6 파이프라인 멱등성:** 재시도·재실행·중간 종료 때 예산 차감, `FETCHING` 고착, SCD2 재반영 결과를 본다. 저장된 응답과 목, 그리고 QA 레이크에서 기존 통합 시험을 쓴다.

### 4.3 기능 정확성
- **모든 API:** 정상값, 경계값, 비정상 입력을 넣어 본다.
  - 경계값: 플랜 최대 기간·페이지 크기, 첫·마지막 달, 0건 달.
  - 비정상 입력: 아주 큰 수, 음수, NaN·Infinity, 잘못된 형식, 13월, 뒤바뀐 기간, 조작된 커서·문자열, 남는 필드, 잘못된 메서드·Content-Type.
  - 확인할 것: 상태 코드, RFC 9457 오류 형식, OpenAPI 스키마 일치, ETag/304.
- **값 대조:** QA 데이터로 API 응답과 ClickHouse 직접 집계를 맞춰 본다.
  - 대상: 건수·해제 제외·중위가·분포 합·단지 순위·커서 페이지가 빠짐이나 중복 없이 이어지는지·데이터셋 버전 갱신 뒤 캐시 무효화.

### 4.4 신뢰성
- **의존 구성요소 장애:** ClickHouse·Redis·PostgreSQL·MinIO 가 느릴 때(toxiproxy 지연·끊김)와 멈출 때(`docker pause`·`stop`) 본다. 응답 코드, 시간 초과, 복구 뒤 정상화, 데이터 상태를 확인한다.
- **재시작:** 부하 중 API 재시작(진행 중 요청), 내보내기 중 작업자 재시작, ClickHouse 재시작.
- **동시 요청:** 같은 요청을 동시에 보낼 때 본다.
  - 대상: 캐시 채우기 중복, 키 발급·폐기, 내보내기 생성, 로그 비우기, 한도 카운터

### 4.5 성능 (QA 스택, 운영 규모의 생성 데이터)
- **핵심 API 부하:** k6 로 지역 통계·거래 목록·분포·단지·시장 개요·검색·경계를 잰다. p50/p95, 처리량, 실패율을 기록한다.
- **느린 질의:** ClickHouse `query_log` 상위.
- **큰 응답:** 크기와 압축 여부.
- **화면 성능:** Lighthouse (모바일·데스크톱, 화면별).
- 운영 스택과 CPU 를 나눠 쓰는 환경이라, 수치에는 측정 조건을 함께 적는다.

### 4.6 화면·UX·접근성
- 내장 브라우저로 8개 메뉴의 버튼·폼·탭·표·정렬·페이지 넘김·테마 전환을 모두 눌러 본다.
  - 수집할 것: 콘솔 오류, 실패한 요청, 중복 요청.
  - 화면 폭 375·768·1280, 키보드만으로 조작하기, 오류·빈 데이터·느린 응답 상태도 본다.
- 접근성: axe-core 로 WCAG 2.1 AA 를 자동 점검한다 (화면별, 밝게·어둡게). 위반 항목을 규칙·요소·영향도별로 정리한다.

### 4.7 회귀
- 기존 시험 전체(파이프라인 단위·API·웹·lint·audit·dbt parse)를 먼저 한 번 돌려 기준선으로 삼고, 끝날 때 다시 돌린다.
- 운영 레이크 통합 시험 2개는 QA 레이크에서 돌린다. 띄울 수 없으면 '검증 못 함'으로 적고 이유를 쓴다.
- 중요한데 시험이 없는 경로를 목록으로 정리한다.

  - `qa/` (스택 override·데이터 생성·점검 스크립트·부하 시나리오)
  - 증거: `docs/qa/evidence/` (로그·스크린샷)
- **마무리 검토:** 처음 보는 리뷰어 역할의 별도 에이전트가 적힌 절차대로 실제로 재현되는지와 심각도가 맞는지 확인한다.
- **PR:** QA 브랜치로 PR 을 열고, 기존 방식대로 Auto-fix 를 켜고 CI 가 통과하면 병합한다.
  - 운영 스택 배포는 하지 않는다. 보고서에 배포 절차를 적는다.

## 6. 멈추고 묻는 경우
- 운영 환경, 실제 계정, 지울 수 없는 데이터로 시험해야 할 때
- 호출 한도나 비용이 있는 외부 서비스를 실제로 불러야 할 때
- 비밀값, 계정, 환경 변수처럼 사용자가 직접 넣어야 하는 값이 필요할 때
- 코드·문서로 기대 동작을 알 수 없어 결함인지 의도인지 판단하기 어려울 때
